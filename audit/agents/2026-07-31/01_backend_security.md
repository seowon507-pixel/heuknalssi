## 4. 확인한 흐름·파일·테스트

### 데이터 흐름과 신뢰 경계

```text
브라우저(localStorage 포함)
  → /api/* (Vercel rewrite)
  → api/gateway.js의 프로세스별 backend 싱글턴
  → HTTP 경계: Origin/CORS → 세션 쿠키 → CSRF → 입력 검증 → 요청 제한/멱등성
  → application/services.js: 후보 소유권·분석 생성·리포트 생성
  → 도메인 규칙·매핑
  → 외부 어댑터: Kakao/기상/토양 등
  → 프로세스 메모리 저장소 및 선택적 Supabase RPC 백업
```

- **브라우저 신뢰 경계:** `ui-integration/backend-client.mjs`가 지역 문자열·농장 프로필·작물 및 설정·계정 키를 `localStorage`에 보관한다. 브라우저 저장소는 서버 인증 경계가 아니며 XSS·공용 단말·기기 분실을 전제로 민감도를 낮춰야 한다.
- **HTTP 신뢰 경계:** `backend-v3/src/api/http-handler.js:583-664`에서 허용 Origin을 정확 비교하고 CORS·CSRF·세션 소유권을 적용한다. 실제 요청에서도 잘못된 Origin은 403, CSRF 없는 변경 요청은 403, 범위를 벗어난 좌표는 400이었다.
- **업무 소유권 경계:** `backend-v3/src/application/services.js:302-369,609-629`에서 후보 토큰과 분석 결과를 세션 소유자에 결속한다. 다른 세션의 객체를 읽는 경로를 기본 허용하지 않는다.
- **외부 네트워크 경계:** `backend-v3/src/adapters/network.js`에 HTTPS·고정 호스트 허용 목록, 응답 크기 2MB 제한, 타임아웃/취소, 제한적 재시도, 리디렉션 차단이 있다. `provider-control.js`는 동시성·대기열·회로 차단을 제한한다.
- **실패 격리:** `application/services.js:853-967,1245-1342`는 외부 소스를 병렬로 호출하고 소스별 실패를 `unavailable` 봉투로 격리해 전체 응답을 무조건 실패시키지 않는다.
- **메모리 상태 경계:** `session-manager.js`, `ttl-memory-store.js`, `idempotency-store.js`, `rate-limiter.js`가 프로세스 로컬 상태를 사용한다. `api/gateway.js`의 싱글턴도 동일한 warm instance 안에서만 재사용된다.

### 보안 헤더와 실제 HTTP 결과

- 세션 쿠키: `HttpOnly`, `SameSite=Lax`, `Path=/` 확인. 로컬 HTTP에서 `Secure`가 없는 것은 개발 환경으로는 예상된 결과다.
- 응답: `Cache-Control: no-store`, CSP, `X-Request-Id` 확인.
- 허용 Origin 응답: `Access-Control-Allow-Origin: http://localhost:3000` 확인.
- `OPTIONS /api/analyses`: 204와 `POST, OPTIONS` 확인.
- 브라우저 콘솔: 확인 시점에 경고·오류 없음.
- 브라우저로 전달되는 정적 자산에서 서버 환경 변수 설정 이름의 직접 노출 흔적을 찾지 못했다. 저장소 추적 파일에는 `.env.example`만 확인했으며 내용은 열지 않았다.

### 테스트와 배포 계약

- `backend-v3/test/backend-e2e.test.js`는 하나의 백엔드 인스턴스만 생성해 검증한다.
- 테스트 전체에서 `api/gateway.js`, Vercel rewrite, cold start, 인스턴스 전환, 프로세스 재시작을 다루는 통합 검사를 찾지 못했다.
- 루트 `npm run verify`와 `.github/workflows/ci.yml`은 UI 테스트·백엔드 검사·백엔드 테스트를 실행하지만 배포 빌드와 gateway 통합 검사를 포함하지 않는다.
- `README.md`도 DB 미사용, 메모리 세션, Vercel 인스턴스 전환 시 흐름 단절 가능성, Supabase 마이그레이션 부재를 명시한다.

## 5. 심각도순 발견 사항

### 확정 결함

#### P0-01. 핵심 다단계 흐름이 프로세스 로컬 상태에 의존해 서버리스 인스턴스 전환 시 깨진다

- **근거:** `api/gateway.js:14-15,63-66`은 warm Lambda별 백엔드 싱글턴을 만든다. 세션은 `session-manager.js:107-134`, 후보·분석은 `application/services.js:215-222`, 멱등성은 `idempotency-store.js:50-149`, 요청 제한은 `rate-limiter.js:9-86`의 메모리에 저장된다. `ttl-memory-store.js:23-29`도 스스로 process-local임을 명시한다.
- **재현:** 같은 세션 비밀값을 가진 독립 백엔드 2개를 실행했다. 첫 인스턴스가 발급한 쿠키·CSRF로 원 인스턴스에 요청하면 정상적으로 입력 검증 단계의 400을 반환했지만, 두 번째 인스턴스에서는 403을 반환했다. 쿠키 서명은 유효해도 서버 측 세션 레코드가 공유되지 않기 때문이다.
- **영향:** 지역 후보 선택 → 후보 토큰 사용 → 분석 생성 → 분석 조회·리포트 생성이 서로 다른 인스턴스에 배정되면 사용자는 무작위 403/404·중복 작업·시연 실패를 겪는다. 요청 제한과 멱등성도 인스턴스마다 달라 우회되거나 중복 처리가 가능하다.
- **최소 수정:** 배포 전 세션·후보 토큰·분석·멱등성·요청 제한을 공유 저장소로 옮기고, 동일 쿠키로 인스턴스를 번갈아 호출하는 통합 검사를 CI에 추가한다. 단순 sticky session은 장애·스케일아웃·cold start를 해결하지 못하므로 최종 해법이 아니다.

#### P1-01. `/api/preflight`의 `READY`가 운영 준비 상태를 과대 표시한다

- **근거:** 실제 응답은 `serviceState=READY`이면서 `persistence=NOT_AVAILABLE`, `deviceBackup=NOT_AVAILABLE`이었다. `application/services.js:703-839`의 readiness는 어댑터 메서드 존재와 규칙·매핑 준비만으로 결정하며, 공유 세션·공유 멱등성·지속 저장·실제 외부 서비스 도달성은 판정에 포함하지 않는다.
- **영향:** 발표자·운영자·자동 헬스체크가 “분석 규칙을 계산할 수 있음”을 “배포 환경에서 사용자 흐름을 끝까지 보장함”으로 오해한다. P0 상태에서도 배포가 정상으로 보인다.
- **최소 수정:** `calculationReady`, `dependencyReachable`, `stateStoreReady`, `deploymentReady`를 분리하고, 최상위 `READY`는 핵심 사용자 여정에 필요한 공유 저장소와 실제 의존성 검사를 모두 통과할 때만 반환한다.

#### P1-02. 사용자 동의 표시와 실제 브라우저 저장 동작·삭제 경로가 일치하지 않는다

- **근거:** `backend-client.mjs:624-635`의 지속 저장 동의 UI는 서버 persistence capability가 없으면 숨거나 비활성화된다. 그러나 후보 선택 시 `:872-876`에서 지역 문자열을, 분석 후 `:941-965`에서 세션을, `:3663-3700`에서 농장 프로필·작물·설정을 동의와 무관하게 `localStorage`에 쓴다. 공급자 지역 문자열은 `src/adapters/kakao.js:109-147`에서 주소 표현을 포함할 수 있다. `clearStoredSession`은 정의되어 있으나 호출 경로를 찾지 못했고, 농장 프로필·지역·계정 키를 한 번에 삭제하는 사용자 경로도 찾지 못했다.
- **영향:** UI상 “저장하지 않음”으로 이해한 사용자의 단말에 위치·재배 맥락이 남을 수 있다. 공용 단말·XSS·기기 분실 시 개인정보 노출 범위가 커지며 삭제·보존 설명도 불가능하다.
- **최소 수정:** 서버 저장 동의와 기기 저장 동의를 별도로 명확히 표시하고, 기본값·보존 기간·저장 항목을 설명한다. 지역 일반화, 전체 로컬 데이터 보기/삭제, 로그아웃 시 계정 키 폐기, TTL을 제공한다.

#### P1-03. Supabase 백업은 `CONFIGURED_UNVERIFIED` 상태에서도 API가 조건부로 활성화된다

- **근거:** `server/config.js:171-194`는 URL과 비밀값이 있으면 `CONFIGURED_UNVERIFIED`로 표시한다. `server/app.js:195-200`은 이 값들만으로 저장소를 만들고, `device-backup.js:90-106`의 `configured`도 비어 있지 않은지만 본다. `http-handler.js:940-968`은 `.configured`가 참이면 직접 API 요청을 허용한다. 저장소에는 요구되는 스키마·RLS·RPC 마이그레이션이 없고 README도 마이그레이션 전 비활성화를 요구한다.
- **조건:** 현재 실제 프리플라이트는 `DISABLED`라 즉시 노출된 결함은 아니다. 그러나 환경 변수 두 개가 설정되는 순간 UI 표시와 달리 직접 API 경로는 활성화되는 코드상 확정 조건부 결함이다.
- **영향:** 불완전한 RLS/RPC·잘못된 프로젝트·스키마 불일치 상태에서 기기 백업이 부분 활성화되어 데이터 격리 실패나 예측 불가능한 오류가 생길 수 있다.
- **최소 수정:** 버전이 고정된 마이그레이션·RLS·RPC 헬스체크를 통과한 경우에만 서버 라우트를 활성화한다. `CONFIGURED_UNVERIFIED`는 반드시 fail-closed로 503을 반환하고 CI에서 격리 정책을 검증한다.

#### P1-04. CI가 실제 배포 진입점과 다중 인스턴스 계약을 검사하지 않아 P0가 통과한다

- **근거:** 270개 백엔드 테스트와 62개 UI 테스트가 모두 통과하지만 `api/gateway.js`는 테스트 대상이 아니며, root `verify`는 배포 빌드·rewrite·두 인스턴스 교차 호출을 포함하지 않는다.
- **영향:** 단일 프로세스에서는 완벽히 녹색인 변경이 실제 배포에서는 핵심 흐름을 중단한다. 현재 P0가 바로 이 공백을 통과했다.
- **최소 수정:** Vercel 진입점으로 세션 생성 → 후보 선택 → 분석 생성 → 조회를 수행하고 단계마다 인스턴스를 바꾸는 검사를 필수 배포 게이트로 둔다. 프로세스 재시작 후 멱등 키 재사용도 검증한다.

#### P2-01. 외부 API 캐시는 fresh-only라 짧은 공급자 장애에서도 안전한 마지막 정상값을 활용하지 못한다

- **근거:** `adapter-call.js:166-199`는 fresh 캐시만 읽고 `staleForMs: 0`으로 쓴다. 공통 네트워크와 회로 차단은 잘 구현됐지만 만료 직후 공급자 장애가 나면 검증된 이전값 대신 즉시 `unavailable/HOLD`로 내려간다.
- **영향:** 장애 격리는 되지만 기상·관측 API의 짧은 장애가 불필요하게 전체 권고의 유용성을 낮출 수 있다.
- **최소 수정:** 데이터 종류별로 허용 가능한 stale 시간을 정의하고, `fetchedAt`, `age`, `sourceState=STALE`, 보수적 신뢰도 하향을 사용자에게 명시한다. 위험도가 높은 현재 관측은 stale 사용을 금지하는 등 소스별 정책이 필요하다.

#### P2-02. 운영 관측성이 요청 단위 로그에 머물러 공급자·캐시·회로 상태를 설명하기 어렵다

- **근거:** `http-handler.js:544-553`의 구조화 로그는 requestId, method, route, status, duration, error code 중심이다. 공급자별 지연·타임아웃·재시도·캐시 hit/stale·회로 상태·분석 단계의 상관관계 지표는 확인하지 못했다.
- **영향:** “왜 오늘 특정 지역만 HOLD인가”, “어느 공급자가 느린가”, “인스턴스 전환으로 실패했는가”를 장애 중 빠르게 구분하기 어렵다.
- **최소 수정:** PII를 제외한 `requestId → analysisId → providerCallId` 추적, 공급자별 latency/error/cache/circuit 지표, 상태 저장소 오류율과 인스턴스 식별자, 경보 기준을 추가한다.

#### P2-03. 비밀값 검사가 백엔드 하위 트리에 한정되고 CI에 저장소 전체 비밀 스캔이 없다

- **근거:** `backend-v3/scripts/check-project.js:6-24`의 검색 루트는 `backend-v3`이며, 루트 CI에서 별도 저장소 전체 비밀 스캐너를 찾지 못했다. 현재 추적 파일과 브라우저 자산에서 실제 비밀 노출은 확인하지 못했다.
- **영향:** 향후 루트·프론트엔드·문서·배포 설정에 잘못 커밋된 키가 기존 검사 범위를 벗어날 수 있다.
- **최소 수정:** 저장소 전체를 대상으로 하는 차단형 비밀 스캔과 산출물 번들 스캔을 CI에 추가하고, 오탐 예외는 파일·패턴·만료 사유를 명시해 제한한다.

### 미확정 위험

#### 미재현 P0 위험. Vercel gateway가 비동기 핸들러를 반환하거나 기다리지 않는다

- `api/gateway.js:32`는 `backend.handler(request, response);`를 호출한 뒤 그 Promise를 `return`/`await`하지 않는다. 로컬 서버에서는 응답을 관찰했지만 실제 Vercel Function 수명주기에서는 응답 전 비동기 작업이 freeze될 가능성이 있다.
- Vercel 공식 문서는 함수 인스턴스가 재사용될 수 있으나 0으로 축소되고, 완료를 기다리지 않은 비동기 작업은 함수 종료 시 중단될 수 있음을 설명한다: [Vercel Functions](https://vercel.com/docs/functions), [inconsistent logs troubleshooting](https://examples.vercel.com/kb/guide/troubleshooting-inconsistent-logs-in-vercel-functions).
- 실제 배포에서 재현하지 않았으므로 확정 결함으로 세지 않았다. 최소 수정은 `return backend.handler(request, response)`로 수명주기를 연결하고 배포 스모크 테스트로 확인하는 것이다.

#### 미확정 P1 위험. 백업 대상 URL 오설정·리디렉션에 대한 서비스 역할 자격 증명 방어가 충분히 명시적이지 않다

- `device-backup.js`는 URL과 비밀값의 존재만 확인하며 허용 호스트·HTTPS 강제·명시적 `redirect: "error"`·상위 AbortSignal 연결이 공통 네트워크 어댑터 수준으로 보이지 않는다.
- 현재 기능은 비활성화되어 있고 실제 자격 증명·리디렉션 동작을 검사하지 않았으므로 위험으로만 기록한다. 프로젝트 URL 허용 목록, HTTPS 강제, 리디렉션 차단, 짧은 timeout, 키 범위 최소화가 필요하다.

## 6. 잘된 점

- Origin을 반사하지 않고 허용 목록과 정확 비교하며, 변경 요청에 세션 결속 CSRF를 요구한다. 실제 HTTP 검사도 이를 확인했다.
- 후보 토큰과 분석 결과의 소유권 검사가 애플리케이션 서비스에 있어 라우트 우회에 덜 취약하다.
- 좌표와 요청 본문을 경계에서 검증하고 오류를 일관된 상태 코드로 반환한다.
- 외부 요청에 HTTPS·호스트 허용 목록·응답 크기·타임아웃·취소·리디렉션 금지·제한적 재시도를 적용했다. SSRF·무한 대기·과대 응답에 대한 기본 방어가 좋다.
- 공급자 호출을 병렬화하면서 개별 실패를 격리하고, 회로 차단·동시성·대기열을 제한한다. 불완전한 데이터를 정상 데이터처럼 숨기지 않는 방향도 적절하다.
- 세션 쿠키의 `HttpOnly`, `SameSite=Lax`, CSP, `no-store`, 요청 ID가 실제 응답에서 확인됐다.
- 프로덕션 지속 저장이 아직 없고 백업이 미검증이라는 사실을 capability와 README에 숨기지 않았다.
- 270개 백엔드 테스트와 62개 UI 테스트는 단일 인스턴스의 계약과 회귀 방지에 유의미한 기반이다.

## 7. 향후 기능과 연결되는 설계 고려사항

### 저장소와 인증·소유권

- **공유 상태 분리:** 농장·필지·작기·분석·할 일·사진 메타데이터는 Postgres 같은 트랜잭션 저장소에 둔다. 세션·후보 토큰·짧은 캐시·요청 제한·멱등성은 원자적 TTL·`set-if-absent`를 지원하는 공유 KV에 둔다.
- **소유권 모델:** `users`, `farms`, `farm_members(role)`, `parcels`, `seasons`를 기준으로 모든 분석·할 일·사진에 `farm_id`를 강제한다. 서버에서 매 요청마다 membership을 확인하고 익명 세션의 농장을 계정으로 이전하는 절차를 별도로 둔다.
- **불변 증거:** `analysis_runs`에는 규칙 버전, 입력 스냅샷, 공급자·관측시각·수집시각, stale 여부, 결과·제한을 불변 기록한다. 최신 상태와 과거 판단의 재현 근거를 분리한다.
- **외부 공개 ID:** 순차 DB ID 대신 추측 어려운 불투명 ID를 사용하고, DB의 FK·RLS와 애플리케이션 권한 검사를 함께 둔다.

### 농장·사진·할 일·작기·위성 확장

- **농장/필지:** 경계 폴리곤은 버전·좌표계·수집 출처를 기록한다. 주소와 정확 좌표는 일반 지역보다 높은 민감도로 분류해 접근·로그·보존을 제한한다.
- **사진:** 객체 저장소와 짧은 signed URL을 사용하고, 업로드 크기·MIME·파일 시그니처·악성 파일·EXIF 위치를 검사한다. 원본과 파생물을 구분하고 체크섬·동의·보존·삭제 tombstone을 기록한다.
- **할 일:** `status`, `due_at`, `recheck_at`, 근거 분석, 작성 주체, 승인 상태를 명시한다. AI가 직접 확정 작업을 쓰지 않고 제안 → 사용자 확인 → 멱등 적용 순서를 지킨다.
- **작기:** 품종·파종/정식일·생육 단계의 유효기간을 버전으로 관리하고, 과거 분석이 현재 작기 변경으로 재해석되지 않게 한다.
- **위성:** 촬영시각·구름량·공간해상도·센서·지수 계산법·결측 영역을 함께 저장한다. 신선도와 구름 임계치를 통과하지 못한 영상은 현재 상태 판단에 사용하지 않는다.

### 비동기 작업과 운영

- 외부 수집·위성 처리·리포트 생성은 outbox/queue 기반 작업으로 분리한다. 작업에는 멱등 키, 상태, 시도 횟수, 지수 backoff+jitter, 취소, worker lease, DLQ와 재처리 권한이 필요하다.
- 동기 API는 `202 + jobId`를 반환하고 조회/재시도 계약을 제공한다. 동일 사용자 행위가 여러 번 도착해도 하나의 업무 결과만 생성되도록 DB unique constraint와 트랜잭션을 함께 사용한다.
- 운영 지표는 요청·분석·작업·공급자 호출을 연결하되 주소·좌표·작물 메모·자격 증명은 로그에 남기지 않는다.

### 개인정보와 데이터 수명주기

- 데이터 종류별 수집 목적, 필수/선택, 보존 기간, 저장 위치(기기/서버/외부 공급자), 내보내기·삭제 방법을 하나의 정책과 UI로 일치시킨다.
- 정확 주소·좌표·필지 경계는 암호화·최소 권한·감사 로그 대상으로 삼고 분석에 충분하면 일반화된 지역만 보존한다.
- 계정 삭제는 DB, 객체 저장소, 캐시, 백업, 파생 데이터까지 추적 가능한 비동기 삭제 작업으로 구현하고 완료/실패를 사용자에게 알린다.

## 8. 최소 개선 우선순위

1. **P0 — 본선 배포 전:** 세션·후보 토큰·분석·멱등성·요청 제한을 공유 저장소로 이동한다. gateway가 백엔드 Promise를 반환하도록 하고 두 인스턴스 교차 호출·프로세스 재시작 스모크 테스트를 통과시킨다.
2. **P1 — 배포 판정 정직성:** preflight를 계산 가능/의존성/상태 저장소/배포 준비로 분리하고, 공유 상태가 없으면 최상위 `READY`를 내리지 않는다.
3. **P1 — 개인정보 통제:** 기기 저장과 서버 저장 동의를 분리하고 저장 항목·TTL을 표시하며, 지역·농장·세션·계정 키 전체 삭제 경로를 제공한다.
4. **P1 — 백업 fail-closed:** 버전 고정 마이그레이션, RPC와 RLS 헬스체크가 검증될 때까지 API를 503으로 닫고 잘못된 URL·권한·tenant 교차 접근 테스트를 추가한다.
5. **P1 — CI 배포 계약:** `npm run build`, 실제 `api/gateway.js`와 rewrite 통합, 다중 인스턴스/재시작/멱등성 검사를 필수 게이트로 추가한다.
6. **P2 — 장애 품질:** 데이터별 stale 허용 정책과 연령·출처 표시를 도입하고, 공급자별 지연·오류·캐시·회로 지표와 경보를 추가한다.
7. **P2 — 공급망·비밀:** 저장소 전체와 빌드 산출물의 비밀 스캔을 CI에 추가한다.

## 9. 남은 불확실성과 실행하지 못한 검사

- 실제 Vercel 배포에서 cold start, 인스턴스 교차 라우팅, 함수 종료 시 비동기 응답 freeze를 재현하지 못했다. 코드와 로컬 두 인스턴스 재현으로 상태 공유 결함은 확정했지만 플랫폼 수명주기 위험은 별도 미확정으로 남겼다.
- Supabase 스키마·RLS·RPC·백업 복원은 프로젝트와 마이그레이션이 없어 실행하지 않았다. 실제 자격 증명이나 환경 파일은 열지 않았다.
- 외부 기상·토양 공급자에 지연·429·5xx·부분 응답·대용량 응답을 실제로 주입하는 장시간 장애 시험은 하지 않았다. 단위·통합 테스트와 구현을 확인했다.
- 부하 시험, 동시 멱등성 race, 요청 제한의 분산 정확성, 메모리 성장·GC·30초 Vercel 제한은 측정하지 않았다.
- 접근성·반응형·과학적 농업 타당성·시각 디자인은 역할 A의 전문 평가 범위가 아니며, 여기 점수는 백엔드가 해당 경험을 얼마나 안정적으로 지원하는지에 한정된다.
- 실제 사용자·실제 농장 데이터로 검증하지 않았고, 현재 로컬 브라우저 상태가 대표 사용자 행동을 의미한다고 가정하지 않았다.
